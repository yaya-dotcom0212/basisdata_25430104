## 2. Ringkasan Dasar Teori

### A. Data Definition Language (DDL)
DDL adalah kelompok perintah SQL yang digunakan untuk mendefinisikan dan mengelola struktur objek basis data seperti *database*, *table*, *index*, dan *constraint*. Perintah utama DDL meliputi:
* `CREATE`: Membuat objek basis data baru (contoh: `CREATE DATABASE`, `CREATE TABLE`).
* `ALTER`: Mengubah struktur objek basis data yang sudah ada.
* `DROP`: Menghapus objek basis data dari sistem.

### B. Data Manipulation Language (DML)
DML adalah kelompok perintah SQL yang digunakan untuk memanipulasi dan mengelola data di dalam tabel. Perintah utama DML meliputi:
* `INSERT`: Menambahkan baris data baru ke dalam tabel.
* `SELECT`: Mengambil/menampilkan data dari satu atau beberapa tabel.
* `UPDATE`: Memperbarui nilai data pada baris yang sudah ada.
* `DELETE`: Menghapus baris data dari tabel.

### C. Integritas Referensial dan Constraint
* **Primary Key (PK):** Identitas unik untuk setiap baris record dalam tabel.
* **Foreign Key (FK):** Kolom yang menghubungkan tabel anak ke tabel induk untuk menjaga relasi entitas.
* **Klausa `ON DELETE CASCADE`:** Aturan integritas referensial yang secara otomatis menghapus baris data pada tabel anak apabila baris terkait pada tabel induk dihapus.
* **Batasan Kolom (*Constraints*):**
  * `NOT NULL`: Memastikan kolom tidak boleh bernilai kosong.
  * `UNIQUE`: Memastikan seluruh nilai dalam kolom bersangkutan bersifat unik (tidak boleh duplikat).
  * `DEFAULT`: Memberikan nilai bawaan jika kolom tidak diisi saat proses `INSERT`.

## 4. Jawaban Titik Analisis

1. **Mengapa klausa `ON DELETE CASCADE` penting pada relasi entitas seperti `kategori_produk` ke `produk` atau `pesanan` ke `detail_pesanan`?**
   * **Jawaban:** Klausa `ON DELETE CASCADE` penting untuk menjaga integritas referensial data (*data integrity*). Ketika baris induk (misalnya data `pesanan`) dihapus, MariaDB secara otomatis akan menghapus seluruh baris anak terkait (pada `detail_pesanan`). Tanpa klausa ini, sistem akan menghasilkan *orphan record* (data yatim tanpa induk) atau menolak proses penghapusan data.

2. **Mengapa atribut `nomor_telepon` dan `nomor_resi` diset dengan tipe data `VARCHAR` dan bukan `INT`/`BIGINT`?**
   * **Jawaban:** Atribut seperti nomor telepon dan nomor resi mengandung angka yang tidak digunakan untuk operasi matematika (penjumlahan/perkalian). Selain itu, nomor telepon sering diawali angka `0` atau karakter `+` (contoh: `0812...` atau `+62812...`). Jika menggunakan tipe data angka (`INT`), angka nol di depan akan otomatis terhapus oleh sistem RDBMS.

3. **Mengapa atribut `email_pengguna` dan `nomor_resi` wajib memiliki batasan `UNIQUE`?**
   * **Jawaban:** Batasan `UNIQUE` memastikan tidak ada dua baris data yang memiliki nilai sama pada kolom tersebut. Pada `email_pengguna`, hal ini mencegah pendaftaran akun ganda dengan email yang sama. Pada `nomor_resi`, hal ini mencegah bentrokan pelacakan paket ekspedisi.

## 7. Pembahasan dan Kendala

### Pembahasan
Pada praktikum Modul 2, pengerjaan berfokus pada desain basis data relasional untuk sistem e-commerce lokal `toko_daring_lampung`. Seluruh struktur tabel dibangun menggunakan DDL dengan menerapkan kunci utama (*Primary Key*), kunci tamu (*Foreign Key*), serta batasan seperti `UNIQUE` dan `DEFAULT`. Pengisian data awal (*seed data*) menggunakan perintah DML `INSERT INTO` berhasil merepresentasikan skenario nyata transaksi penjualan barang, pembayaran, hingga pelacakan pengiriman resi.

### Kendala dan Solusi
1. **Kendala:** Muncul kesalahan `ERROR 1215 (HY000): Cannot add foreign key constraint` saat mengeksekusi skrip pembuatan tabel `produk`.
   * **Solusi:** Memastikan tabel induk (`kategori_produk`) dibuat terlebih dahulu sebelum tabel anak (`produk`) dieksekusi agar kunci referensi sudah terdefinisi.
2. **Kendala:** Terjadi kesalahan *Foreign Key Constraint Fail* saat memasukkan data ke tabel `pesanan`.
   * **Solusi:** Memeriksa nilai `id_pembeli` pada tabel `pengguna` dan menyelaraskan urutan eksekusi `INSERT INTO` dari tabel induk ke tabel anak.
3. **Kendala:** Format jam dan tanggal pada baris `tanggal_pesanan` sempat tidak konsisten.
   * **Solusi:** Membakukan format string tanggal ISO `YYYY-MM-DD HH:MM:SS` untuk seluruh kolom bertipe tanggal/waktu.
